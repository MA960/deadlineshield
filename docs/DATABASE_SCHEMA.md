# DeadlineShield database schema

## Overview

The backend uses PostgreSQL through Spring Data JPA and Hibernate. Entity mappings are under `src/main/java/com/deadlineshield/backend/model`. The current application configuration uses:

```properties
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
```

Hibernate therefore updates the schema to match the mapped entities at application startup. The table/column descriptions below are the logical schema derived from those mappings. Exact generated names, SQL types, indexes, and constraint names can vary with Hibernate and PostgreSQL versions; inspect the target database metadata for the deployed DDL.

## Tables

All entity primary keys are UUIDs generated by Hibernate/JPA. `Instant` values are stored as PostgreSQL timestamp values with time-zone semantics according to Hibernate's PostgreSQL dialect and version. String lengths and physical column names not explicitly customized in the entity are Hibernate defaults.

### `organizations`

| Column | Meaning |
|---|---|
| `id` | UUID primary key. |
| `name` | Organization name. |
| `created_at` | Creation instant, initialized by the application when an entity is constructed. |

An organization has a one-to-many relationship to projects. The `projects` collection is the inverse side, mapped by `projects.organization_id`.

### `projects`

| Column | Meaning |
|---|---|
| `id` | UUID primary key. |
| `name` | Project name. |
| `description` | Optional project description. |
| `adjusted_target_date` | Optional adjusted deadline. |
| `created_at` | Creation instant, initialized by the application. |
| `organization_id` | Required foreign key to `organizations.id`. |

A project has a one-to-many relationship to milestones. The collection is mapped by `milestones.project_id`.

### `milestones`

| Column | Meaning |
|---|---|
| `id` | UUID primary key. |
| `name` | Milestone name. |
| `due_at` | Optional milestone due instant. |
| `token` | Required, unique UUID used by the client review link; marked non-updatable in JPA. |
| `clock_paused` | Required boolean indicating whether the clock is paused. |
| `paused_at` | Optional instant when the current pause began. |
| `review_feedback` | Optional client feedback. |
| `reviewed_at` | Optional review-submission instant. |
| `status` | Required string enum: `PENDING` or `APPROVED`. |
| `project_id` | Required foreign key to `projects.id`. |

The token is generated in the entity constructor. The repository applies a pessimistic write lock when looking up a milestone by token to prevent concurrent reuse of the review link.

### `audit_logs`

| Column | Meaning |
|---|---|
| `id` | UUID primary key. |
| `action` | Audit action name, such as `MILESTONE_CLOCK_PAUSED` or `MILESTONE_REVIEWED`. |
| `details` | Human-readable event detail; pause reasons are recorded here. |
| `occurred_at` | Event instant, initialized by the application. |
| `project_id` | Optional foreign key to `projects.id`. |
| `milestone_id` | Optional foreign key to `milestones.id`. |

## Relationships and delete behavior

```text
organizations 1 ─── * projects 1 ─── * milestones
                         │                 │
                         └──── * audit_logs ┘
```

- `Project.organization` is required. `Organization.projects` uses `CascadeType.ALL` and `orphanRemoval=true`.
- `Milestone.project` is required. `Project.milestones` uses `CascadeType.ALL` and `orphanRemoval=true`.
- `AuditLog.project` and `AuditLog.milestone` are optional many-to-one references and have no JPA remove cascade. Removing a referenced project or milestone can therefore be restricted by its audit-log foreign keys unless the audit record is first retained/referenced appropriately.
- JPA cascade and orphan-removal behavior is applied by the ORM when deleting through the entity relationships. It is not necessarily a PostgreSQL `ON DELETE CASCADE` constraint.
- There is no explicit unique constraint on entity names or project/milestone deadlines. The milestone `token` is explicitly unique and non-null.

## Audit log and immutability

Clock pause and client review operations create audit-log records inside the same transaction as the state changes. A transaction rollback should roll back both the operation and its associated audit write.

**Important limitation:** The current code does not enforce audit-log immutability. `AuditLog` has Lombok setters, `AuditLogRepository` extends `JpaRepository` (including delete operations), and the schema does not define append-only triggers or restricted database permissions. Audit entries are written as an application convention, not a tamper-proof compliance record.

For production audit guarantees, use a dedicated database role that cannot update or delete audit rows, enforce append-only behavior with database permissions and/or triggers, restrict administrative access, and export records to a separately controlled immutable/WORM store. Introduce and review explicit schema migrations before changing production constraints.

## Schema management recommendations

- Keep `ddl-auto=update` for local development only. Production deployments should use versioned migrations (for example, Flyway or Liquibase) and `ddl-auto=validate`.
- Review generated DDL for the target PostgreSQL/Hibernate versions, including FK delete actions, indexes, nullability, and timestamp precision.
- Back up the database before schema changes and test migrations against a copy of production data.
- `spring.jpa.show-sql=true` is enabled in the current properties and should normally be disabled or appropriately controlled in production.
